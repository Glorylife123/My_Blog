AI 编程工具使用记录（二）：Claude Code 和 Codex 对比，为什么我最后选择 Codex

AI 编程工具使用记录（二）：Claude Code 和 Codex 对比，为什么我最后选择 Codex

Echo2026-06-122026-06-12

系列说明

这是“AI 编程工具使用记录”系列的第二篇。

上一篇主要写 Codex 的使用方式：从直接登录 OpenAI 账号，到后来通过 ccswitch 调 API。
这一篇继续往后写，把 Claude Code 和 Codex 放在一起对比，最后说明为什么我还是选择 Codex 作为主力。

这个系列不是官方教程，更像是我自己的工具迁移记录。

这篇写什么

这篇记录一下我对 Claude Code 和 Codex 的使用感受。

这两个工具的定位都很接近：都是面向开发者的 AI 编程助手，都不是单纯聊天，而是可以结合项目文件、终端命令和代码修改来工作。

我一开始并没有特别明确地站队，只是都试了一下。用下来之后，我最后更倾向于把 Codex 放进自己的日常开发流程里。

这篇不做参数表式的硬评测，也不写成“谁吊打谁”。更多是从我自己的使用习惯出发，写清楚为什么最后选择 Codex。

我对这类工具的期待

在对比之前，先说一下我对 AI 编程工具的期待。

我不太需要它只做一个“高级搜索引擎”，也不希望它只是给我贴一段代码。我更希望它能做到：

  • 看懂当前项目结构
  • 知道哪些文件该改，哪些文件不该动
  • 修改之前先说明思路
  • 修改之后能跑构建或测试验证
  • 出问题时能继续定位，而不是让我重新描述一遍

也就是说，我想要的不是一个单次问答工具，而是一个能参与项目维护的终端助手。

从这个角度看，Claude Code 和 Codex 都比普通网页对话更适合写代码。

Claude Code 给我的第一印象

Claude Code 的第一印象是比较顺手。

它很适合做这种事情：

  • 快速理解一个文件
  • 根据自然语言改一段代码
  • 帮忙解释报错
  • 生成一段比较完整的实现思路

Claude 系列模型在长文本理解和表达上一直给我感觉比较稳，所以 Claude Code 在阅读代码、总结逻辑、解释项目结构时，体验是不错的。

如果只是让它看一段代码，然后问“这里为什么报错”“这个函数做了什么”“帮我改成另一种写法”，它完成得很自然。

Claude Code 用起来的问题

但真正放到我的开发流程里之后，我会遇到几个不太舒服的点。

1. 工作流不够贴合我的习惯

我更习惯先让工具检查项目，再给出计划，然后小范围修改，最后跑命令验证。

Claude Code 当然也能做这些事，但在我的体验里，它更像是一个很强的代码对话助手，而不是我最终想固定下来的“项目维护工具”。

它适合快速帮我解决一个点，但我不太想把整个仓库清理、配置调整、文章生成、构建验证这些连续流程都交给它。

2. 配置管理不是我最喜欢的方式

我现在更倾向于把模型调用这件事配置化，比如 API、模型、服务地址都能自己管理。

如果一个工具更依赖自己的账号体系和默认配置，我会觉得可控性弱一点。不是不能用，而是不太符合我现在对开发工具的管理方式。

我更希望它像 Git、Node、Hexo 这类工具一样：配置明确，行为透明，换环境时也比较容易迁移。

3. 接口生态反而是 Claude Code 更灵活

这里要单独说一下接口生态。

如果只看模型接入范围，Claude Code 其实更灵活。它不只局限在一种接口形态里，很多第三方模型服务都可以折腾接入，比如 DeepSeek、小米 MiMo 这类模型。

Codex 这边我目前的使用感受是，走 API 时主要还是围绕 OpenAI 的 Responses 接口来用。这样做的好处是路径更标准，和 OpenAI 自家的模型配合更顺；但问题也很明显：如果想随手切到 DeepSeek、小米 MiMo 这类模型，空间就没有 Claude Code 那么大。

所以如果一个人的核心需求是“尽可能多地接不同模型”，那 Claude Code 在这一点上确实更有优势。

但对我来说，模型接入范围不是唯一标准。
我更看重的是它放进真实项目之后，能不能稳定地读项目、改文件、跑验证、收尾。

这也是为什么即使 Claude Code 的接口生态更开放，我最后还是更偏向 Codex。

4. 我更在意“可维护性”

很多时候我不是让 AI 写一个 demo，而是在维护一个真实项目。

真实项目里最怕的不是“写不出来”，而是：

  • 改多了
  • 改偏了
  • 顺手修了不该修的东西
  • 没有验证就告诉我完成了

所以我会更看重工具在修改边界、计划执行和验证反馈上的稳定感。

Codex 给我的第一印象

Codex 给我的第一印象更像一个“终端里的协作者”。

它的使用方式天然围绕项目展开：

  • 先看文件结构
  • 再读关键配置
  • 然后给出修改计划
  • 接着改文件
  • 最后跑构建或测试

这套流程和我平时自己维护项目的节奏很接近。

比如这个博客项目里，我让 Codex 检查有没有冗余的地方，它不是一上来就乱删，而是先看 package.json、.gitignore、_config.yml、主题配置和文章目录，再判断哪些东西可以清理。

这种感觉比单纯“回答我怎么做”更像是在一起处理一个项目。

我更喜欢 Codex 的地方

1. 过程更透明

Codex 在做事时，我能看到它准备做什么、正在看什么文件、为什么要改某个地方。

这点对我很重要。

因为我不希望 AI 工具像黑盒一样直接告诉我“我改好了”。我更希望它每一步都有理由，尤其是在涉及删除文件、改依赖、跑命令的时候。

透明不只是为了放心，也是为了后面出问题时能回溯。

2. 更适合仓库级任务

Codex 很适合处理这种跨文件任务：

  • 清理冗余依赖
  • 修改配置并同步文档
  • 新增文章并运行构建
  • 根据报错定位项目问题
  • 检查哪些文件是生成产物，哪些文件应该进版本控制

这些任务不是单点代码补全，而是需要理解整个项目状态。

在这类场景里，我更愿意用 Codex。

3. 和终端工作流更贴合

我平时维护博客基本就是终端工作流：

Codex 正好可以接在这个流程里。

它不只是告诉我“你应该运行构建”，而是可以实际运行，然后根据输出继续判断下一步。

比如构建失败，它可以继续看报错；审计有漏洞，它可以判断是依赖问题还是插件残留；文章 front matter 有问题，它也能直接定位。

这种连续性是我最后选择它的重要原因。

4. 配合 API 使用更灵活

上一篇我写过，我最后更倾向于通过 ccswitch 调 API 来使用 Codex。

这样做之后，模型、接口、密钥这些配置都更明确。对我来说，这比单纯登录某个账号更符合开发习惯。

我可以把它当成开发环境的一部分，而不是一个临时打开的工具。

这点也是我选择 Codex 的原因之一：它更容易被纳入我自己的工具链。

两者简单对比

如果按我的使用感受来总结，大概是这样：

对比点 Claude Code Codex
第一印象 对话和解释能力强 更像终端协作者
适合任务 单点代码理解、解释、改写 仓库级修改、配置清理、验证流程
工作方式 更偏代码助手 更偏项目维护助手
接口生态 更灵活，可接 DeepSeek、小米 MiMo 等模型 目前更偏 OpenAI Responses 接口
我在意的优势 阅读和表达顺滑 过程透明、执行闭环更强
最终定位 偶尔辅助 日常主力

当然，这个表不是客观排名，只是我自己的使用取舍。

如果一个人主要需求是解释代码、生成函数、写局部逻辑，Claude Code 可能已经很好用了。
但如果像我这样，经常围绕一个真实项目做连续修改，我会更偏向 Codex。

为什么最终选择 Codex

最后选择 Codex，其实不是因为 Claude Code 不好，而是 Codex 更符合我的工作方式。

我最看重的是这几点：

  • 能围绕本地项目持续工作
  • 修改前后有清晰过程
  • 能把命令执行和结果验证串起来
  • 更适合处理配置、依赖、文档、文章这类综合任务
  • 配合 API 使用时更容易纳入自己的工具链

对我来说，一个 AI 编程工具要成为主力，不能只会“写代码”。

它还要能理解项目、控制修改范围、验证结果，并且在出错时继续排查。

Codex 在这些方面给我的感觉更稳。

我的结论

Claude Code 和 Codex 都值得试。

如果只是轻量使用，Claude Code 的体验并不差，尤其是解释代码和整理思路时很顺手。

但如果要在真实项目里长期使用，我最后还是会选 Codex。

原因很简单：
它更像一个能参与完整开发流程的助手，而不是只在旁边回答问题的助手。

所以我现在的选择是：

  • Claude Code：作为备用工具，适合偶尔对比思路
  • Codex：作为主力工具，负责日常项目维护和内容生产

对我来说，这个分工比较自然，也更符合现在的使用习惯。
