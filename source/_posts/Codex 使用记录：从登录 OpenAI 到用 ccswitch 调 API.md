## 系列说明

这是“AI 编程工具使用记录”系列的第一篇。

这个系列主要记录我自己折腾 AI 编程工具的过程，不追求写成完整教程，更偏向实际使用后的取舍和总结。

目前这个系列暂时分成两篇：

- 第一篇：Codex 从登录 OpenAI 到用 `ccswitch` 调 API
- 第二篇：Claude Code 和 Codex 对比，为什么最后选择 Codex

这一篇先写 Codex 本身的使用方式，下一篇再把它和 Claude Code 放在一起比较。

---

## 这篇写什么

这篇记录一下我最近使用 Codex 的过程，主要写两种用法：

- 直接登录 OpenAI 账号使用
- 通过 `ccswitch` 调用 API 使用

一开始我用的是第一种方式，因为上手最简单，基本就是登录账号，然后直接在终端里让 Codex 帮我看项目、改代码、跑命令。后面用了一段时间之后，我慢慢改成了第二种方式，也就是用 `ccswitch` 管理接口和模型，再让 Codex 走 API。

这篇不写成官方教程，主要记录我自己的使用体验和取舍。

---

## 最开始：直接登录 OpenAI 账号

刚开始接触 Codex 的时候，我的想法很简单：先跑起来再说。

这种方式的流程比较直观：

1. 安装 Codex CLI
2. 在终端里启动 Codex
3. 按提示登录 OpenAI 账号
4. 授权之后开始使用

优点也很明显：

- 配置少
- 不需要自己管理 API Key
- 对新手比较友好
- 登录成功后基本可以直接进入工作流

如果只是临时体验，或者只是让 Codex 帮忙解释一段代码、改一个小 bug，这种方式确实很舒服。

---

## 直接登录方式的问题

但用久一点之后，我发现这种方式也有一些不太适合我的地方。

首先是可控性不够强。  
我更希望自己能明确知道当前走的是哪个接口、哪个模型、哪个服务地址，以及后续要不要切换到别的配置。

其次是环境迁移不够顺手。  
如果换电脑、换终端环境，或者在不同项目之间切换，我不太想每次都重新处理登录状态。登录账号这种方式适合“单点使用”，但不太适合我这种经常折腾开发环境的人。

还有一点是心理上的：  
我更习惯把 AI 工具当成开发链路里的一个组件，而不是一个绑定账号状态的黑盒。既然它最终也是在和模型交互，那我更希望这部分配置能像数据库连接、部署密钥一样被明确管理。

---

## 后来：用 ccswitch 调 API

后面我开始改成用 `ccswitch` 来管理 API 调用。

我这里对它的定位很简单：  
`ccswitch` 更像是一个“接口切换器”或者“配置中间层”，把模型、接口地址、密钥这些东西统一管起来。Codex 需要调用模型时，就不再完全依赖账号登录状态，而是走我配置好的 API。

这样做之后，整个使用方式变成了：

1. 在 `ccswitch` 里配置 API Key
2. 配置接口地址和默认模型
3. 根据需要切换不同的服务或模型
4. 让 Codex 通过 API 完成代码阅读、修改和命令执行

这个流程比直接登录稍微麻烦一点，但一旦配置好，后面会更稳定。

---

## 两种方式的对比

如果简单对比，我会这样理解：

| 使用方式 | 优点 | 问题 | 适合场景 |
| --- | --- | --- | --- |
| 登录 OpenAI 账号 | 上手快、配置少、适合体验 | 可控性弱、迁移不够顺手 | 临时使用、轻量体验 |
| `ccswitch` 调 API | 可控性强、方便切换、适合长期使用 | 初始配置多一点 | 长期开发、多环境、多模型切换 |

我不是说登录账号不好，而是它更像“开箱即用”的方案。  
`ccswitch` 调 API 则更像“工程化使用”的方案。

如果只是偶尔用一下，直接登录就够了。  
但如果打算把 Codex 放进日常开发流程里，经常让它读项目、改代码、跑测试、整理文档，那我更推荐后者。

---

## 为什么最后选择 ccswitch

我最后选择 `ccswitch`，主要是因为这几个原因。

### 1. 配置更透明

API Key、接口地址、模型名称都能自己看见，也能自己管理。

这对我很重要，因为我不想在使用工具时完全不知道它背后走的是什么配置。尤其是在不同模型、不同服务之间切换时，透明配置能减少很多不确定性。

### 2. 切换更方便

有时候我只是想写文章、改 Markdown，不一定需要很强的模型。  
有时候我要让 Codex 看比较复杂的项目、改一串代码、分析报错，这时候就希望换成更强的模型。

用 `ccswitch` 之后，切换这件事会自然很多，不需要每次都重新折腾登录或者环境。

### 3. 更适合长期使用

直接登录适合“现在马上用一下”。  
API 配置适合“以后一直用”。

对我来说，Codex 不是一个偶尔打开的玩具，而是可以放进日常开发流程里的工具。既然要长期用，那我就更希望它的配置方式稳定、可迁移、可维护。

### 4. 更符合开发习惯

开发里很多东西本来就是配置化的：

- 数据库连接
- 部署 Token
- GitHub Access Token
- 环境变量
- CI/CD Secrets

所以把 Codex 的模型调用也配置化，对我来说更顺手。

---

## 实际使用时我怎么分工

现在我的使用方式大概是这样：

- 小问题：直接让 Codex 看当前文件并解释
- 改配置：让 Codex 先检查项目结构，再给出修改方案
- 写文章：先给主题和风格，让它参考已有文章生成初稿
- 修 bug：先让它复现或定位，再小范围修改
- 清理项目：让它找冗余依赖、无用文件和配置残留

这类任务都很适合 Codex，因为它不是单纯聊天，而是能结合本地项目上下文工作。

比如这次博客项目清理，我就更喜欢让它先看 `package.json`、`_config.yml`、主题配置和文章目录，再决定哪些东西能删，哪些东西不能动。

这种工作流比单纯复制代码到网页对话框里舒服很多。

---

## 使用 Codex 时的一点经验

用了一段时间之后，我觉得最重要的不是“让 AI 一次性把所有事做完”，而是要把任务拆清楚。

比较舒服的提问方式是：

```text
先检查项目结构，找出可能冗余的地方，不要直接删除。
```

或者：

```text
参考现有文章风格，帮我新增一篇同风格文章，并运行构建验证。
```

这样 Codex 会更容易按步骤做事，也更不容易改到不该改的地方。

如果一上来就说“帮我优化一下项目”，范围太大，它可能会不知道优化到什么程度才算合适。

---

## 我的结论

如果只想快速体验 Codex，直接登录 OpenAI 账号是最省事的方式。

但如果是长期开发使用，我更推荐用 `ccswitch` 调 API。原因不是它更酷，而是它更可控、更稳定，也更符合开发者对工具链的管理习惯。

简单说就是：

- 想快速开始：登录 OpenAI 账号
- 想长期使用：`ccswitch` 调 API

我最后选择后者，是因为我希望 Codex 不只是一个临时助手，而是变成自己开发环境里一个可以长期维护的工具。
